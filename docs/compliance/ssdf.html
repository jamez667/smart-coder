NIST · version 1.0.0 · generated 2026-08-01T20:01:12Z

This is not a compliance attestation. It is the output of an automated scan of source code, showing what could and could not be evidenced from a repository. Most of any framework is organizational and cannot be assessed this way — those controls are reported as unknown, which is a statement about the tool's visibility, not about the organization. Certification requires an accredited auditor.

File paths, line numbers and evidence excerpts are withheld from this published version.

Scope and limitations

This pack inspects source-controlled artifacts only. It cannot observe build infrastructure, signing key custody, developer training records, or vulnerability disclosure handling. SSDF is unusually amenable to source inspection because it governs the software production process itself. Even so, roughly half of its practices are organizational and are declared undeterminable here rather than omitted. A passing result is evidence toward a practice, never a completed attestation. The CISA secure software development attestation form requires an authorised signatory, not a scanner.

PS.1unknownProtect all forms of code from unauthorized access and tampering

Store all forms of code — source, executables, configuration-as-code — based on the principle of least privilege, so only authorized personnel can change it.

weighted: 71% of evidence weight was indeterminate

Evidence to obtain
  • Export of Version Control System (VCS) access control lists and branch protection rules
  • Quarterly access review sign-off sheets for repository permissions
  • Ticketing history showing approvals for granting and revoking developer access

Usually held by: IT Access Management / Engineering Leadership

What an auditor will probe: Show me the access request and approval tickets for the last three developers granted write access, and the offboarding logs for the last terminated employee.

Obtain: Enforce branch protection with required review, define code owners, and keep the protection configuration as code where the provider allows it.

PS.3unknownArchive and protect each software release

Preserve release artifacts and their provenance, and collect, maintain and share provenance data for all components of each release — including an SBOM.

weighted: 2.0/5.0 observable = 40% (pass>=60%, gap<30%)

Evidence to obtain
  • Logs from the artifact repository demonstrating immutable storage of past releases
  • Dynamically generated SBOMs and provenance attestations from recent CI/CD pipeline runs
  • Cryptographic signatures or hashes associated with archived release artifacts

Usually held by: Release Engineering / DevOps

What an auditor will probe: Walk me through the retrieval of a historical release artifact from six months ago and demonstrate how its integrity is verified against the archived SBOM.

Obtain: Generate an SBOM in CI and attach it to each release; retain build provenance attestations.
