This is not a compliance attestation. It is the output of an automated scan of source code, showing what could and could not be evidenced from a repository. Most of any framework is organizational and cannot be assessed this way — those controls are reported as unknown, which is a statement about the tool's visibility, not about the organization. Certification requires an accredited auditor.

File paths, line numbers and evidence excerpts are withheld from this published version.

Scope and limitations

This pack inspects source-controlled build definitions. It cannot observe the build platform itself, signing key custody, or the runtime integrity of the builder — and SLSA levels are ultimately properties of that platform. What this pack CAN evidence: that a build requests provenance, that artifacts are signed, that dependencies are pinned and inventoried, and that the build is reproducible in intent. What it CANNOT evidence: that the builder is isolated, that provenance is unforgeable, or that keys are held securely. Treat a passing result as "the repository asks for the right things". Level attestation requires verifying the platform.

Gaps and manual evidence

Controls that did not pass. Unknown means the tool could not determine the answer from source — these are tasks for an auditor, not findings against the codebase.

SLSA-B-L2gapBuild L2 — hosted build platform with signed provenance

The build runs on a hosted platform that generates and signs provenance. This prevents a developer from forging provenance on their own machine, though it does not yet protect against a compromised build itself.

all-of: worst of 2 check(s) is gap

Remediation: Move builds to a hosted CI platform and sign the provenance (keyless signing via Sigstore is the usual route).

SLSA-B-L1unknownBuild L1 — provenance exists and the build is scripted

The build process is fully scripted and automated, and generates provenance describing how the artifact was built. Provenance at L1 need not be tamper-proof; it must merely exist and be available to consumers.

weighted: 2.0/5.0 observable = 40% (pass>=60%, gap<30%)

Evidence to obtain
  • CI/CD build logs demonstrating the execution of the automated build script for a recent release
  • A sample of the generated provenance file (e.g., in-toto format) corresponding to a specific release artifact
  • Screenshots or directory listings showing the provenance file published and available alongside the final artifact

Usually held by: DevOps / Release Engineering

What an auditor will probe: Can you demonstrate that a consumer downloading the final artifact can successfully locate and download the corresponding provenance file for that exact version?

Obtain: Define the build in a CI workflow and emit a provenance attestation (slsa-github-generator, or in-toto/cosign attest in another platform).

SLSA-B-L3unknownBuild L3 — hardened builds, non-falsifiable provenance

The build platform runs each build in an isolated environment and prevents secret material used to sign provenance from being accessible to user-defined build steps, making provenance non-falsifiable.

all-of: worst of 2 check(s) is unknown

Evidence to obtain
  • CI/CD pipeline configuration files showing the invocation of a recognized trusted builder (e.g., SLSA GitHub generator)
  • CI provider documentation or architectural whitepapers detailing the logical isolation of the build environment
  • Audit logs from the build platform showing that provenance signing is executed by a control plane service, not within the user-defined build steps

Usually held by: DevSecOps / CI Platform Provider

What an auditor will probe: How do you ensure that a malicious script introduced into the build steps cannot extract the signing key or forge the provenance payload before it is signed?

Obtain: Use a reusable trusted builder (e.g. slsa-github-generator) rather than signing inside your own job, and pin all actions to immutable digests.

SBOM-1unknownA software bill of materials is produced for each release

Produce a machine-readable inventory of components for each release, in a standard format (SPDX or CycloneDX), so consumers can assess exposure to a newly disclosed vulnerability.

any-of: no mechanism evidenced, and 1 of 2 check(s) were indeterminate

Evidence to obtain
  • Sample SPDX or CycloneDX files generated for the last three production releases
  • CI/CD pipeline execution logs showing the automated SBOM generation step completing successfully during the release process
  • Artifact repository records showing the SBOMs stored and versioned alongside their respective release binaries

Usually held by: Release Engineering / Product Security

What an auditor will probe: When a new release is cut, how is the SBOM automatically distributed or made available to downstream consumers without manual intervention?

Obtain: Generate an SBOM in CI (syft, cyclonedx-*, sbom-tool) and attach it to the release.

SLSA-S-1unknownSource track — version controlled and change-reviewed

Every change to the source is tracked in version control and reviewed by a second person before it is incorporated, so a single compromised account cannot introduce a change unilaterally.

weighted: 100% of evidence weight was indeterminate

Evidence to obtain
  • Source code management (SCM) branch protection rule configurations showing mandatory approvals required before merging
  • A sample of 3-5 recently merged pull requests showing the distinct identities and timestamps of the author and the reviewer
  • SCM audit logs showing the history of changes to branch protection rules to verify they have not been temporarily disabled

Usually held by: Engineering Manager / DevSecOps

What an auditor will probe: How do you prevent repository administrators from bypassing the two-person review requirement or approving their own pull requests?

Obtain: Require pull-request review with at least one approver and forbid direct pushes to the default branch. Retain the configuration as code where possible.

SLSA-P-1unknownBuild platform isolation and key custody

The build platform isolates builds from one another, prevents user-defined steps from accessing provenance signing material, and protects the signing keys.

all-of: worst of 1 check(s) is unknown

Evidence to obtain
  • SOC 2 Type II report or equivalent third-party security attestation from the CI/CD platform provider covering tenant isolation
  • Architecture diagrams or provider documentation detailing the build platform's Key Management Service (KMS) integration and key custody model
  • Platform provider's technical documentation on ephemeral runner isolation and teardown procedures

Usually held by: Security Lead / CI Platform Provider

What an auditor will probe: What independent third-party assessments validate the CI provider's claims that cross-tenant build environments are strictly isolated and signing keys are physically or logically inaccessible to build runners?

Obtain: Obtain the CI provider's isolation documentation and evidence of signing key custody (KMS/HSM policy, or Sigstore keyless configuration).

SBOM-3unknownBuilds are reproducible in intent

The build environment is pinned so the same source produces the same artifact, allowing an independent rebuild to detect tampering.

all-of: worst of 2 check(s) is unknown

Evidence to obtain
  • Build manifests (e.g., Dockerfiles, lockfiles) showing base images and dependencies pinned by cryptographic digest (SHA256) rather than mutable tags
  • Documented procedures for conducting an independent rebuild of a historical artifact
  • Execution logs or reports from a recent independent rebuild test comparing the resulting artifact hashes against the original release

Usually held by: Lead Developer / DevOps

What an auditor will probe: If we check out a commit from six months ago and run the build today, what mechanisms guarantee the exact same toolchain and dependencies are fetched to produce a bit-for-bit identical artifact?

Obtain: Pin the toolchain and base images to explicit versions or digests.
