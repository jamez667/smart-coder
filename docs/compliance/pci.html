Scope and limitations

PCI DSS governs the Cardholder Data Environment. This pack inspects a source repository, which is at most one component of that environment and frequently sits entirely outside it. Evidenced here: Requirement 6 (secure development, secure coding, code review, change control, script integrity), plus the code-visible slivers of Requirement 3 (do not store sensitive authentication data) and Requirement 8 (no shared or hardcoded credentials). NOT evidenced, and declared explicitly: network segmentation (Req 1), default passwords on infrastructure (Req 2), stored-account-data protection at rest (most of Req 3), transmission encryption across public networks (Req 4), anti-malware (Req 5), physical access (Req 9), logging and monitoring across the CDE (Req 10), penetration testing and ASV scans (Req 11), and policy/programme governance (Req 12). Scope determination is a QSA's first question and this tool cannot answer it. A clean result here says nothing about PCI compliance overall.

PCI-6.4.3unknownPayment page scripts are managed and their integrity assured

All payment page scripts loaded and executed in the consumer's browser are managed: a method is implemented to confirm each script is authorized, a method assures the integrity of each script, and an inventory of scripts with written business justification is maintained. This requirement is new in v4.0 and exists because of Magecart-style skimming.

any-of: no mechanism evidenced, and 1 of 2 check(s) were indeterminate

Evidence to obtain
  • Maintained inventory document of all scripts loaded on payment pages, including the written business justification for each
  • Live configuration exports of Content Security Policy (CSP) headers or Subresource Integrity (SRI) hashes from the production web server/CDN
  • Change management tickets showing the approval workflow and integrity hash generation for a recently added or updated payment page script

Usually held by: Frontend Engineering / Security Lead

What an auditor will probe: Walk me through the ticket history for a recent marketing or analytics script addition to prove it was authorized, justified in the inventory, and had its integrity hash updated before going live.

Obtain: Add subresource integrity (SRI) hashes to every external script tag and adopt a Content-Security-Policy restricting script sources.

Evidence to obtain
  • Inventory of all SSL/TLS certificates used in the CDE, including their expiration dates and issuing CAs
  • Configuration exports from load balancers, web servers, or API gateways showing that deprecated protocols (e.g., TLS 1.0/1.1) and weak ciphers are disabled

PCI-6.2.3unknownBespoke and custom software is reviewed prior to release

Bespoke and custom software is reviewed prior to being released into production to identify and correct potential coding vulnerabilities. Reviews are performed by individuals other than the originating author, and either manually or via automated code review tools.

weighted: 67% of evidence weight was indeterminate

Evidence to obtain
  • Version control system (VCS) branch protection configuration settings showing that at least one approving review is required before merging
  • A sample of 5-10 recently merged pull requests from the VCS showing the original author and the distinct, timestamped approval from a second developer
  • Logs or tickets showing how exceptions or emergency fixes bypass the standard review process and how they are reviewed post-release

Usually held by: Engineering Manager / DevOps Lead

What an auditor will probe: Show me a recent pull request for a critical component to prove that the person who wrote the code is not the same person who approved it, and demonstrate that branch protections cannot be bypassed by the author.

Obtain: Require pull-request review by someone other than the author, and retain the branch protection configuration as code where the provider allows it.
